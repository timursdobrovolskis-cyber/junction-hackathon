# Financial calendar

Run `npm run dev:app` from the repository root, then open
http://127.0.0.1:4174/spendvest.html#calendar. The device preview at
http://127.0.0.1:4174/preview.html also includes the Calendar tab. Home and Coach
remain separate sections. No Gemini key is needed for the calendar.

## User experience

- Browse a month grid and select a day; open a payment for its amount, estimated
  date window, recurrence, source explanation and supporting transaction IDs.
- Filter costs, income, or yearly renewals. A payment window may cover multiple
  day cells, but its entry appears once in the month agenda.
- Inspect the Python engine's end-of-day balance on covered dates. Central
  below-buffer days and possible scenario breaches are distinguished. No balance
  is extrapolated after the engine's actual horizon.
- Navigate future months to see recurring reminders. All detected recurrence
  remains uncertain; none is called a confirmed subscription or paid bill.
- Data errors retain the previous successful example and explain the failure.

The default transaction example uses CUST00005, observed through 30 September
2026. It begins in October, not the user's current month. Home's November numbers
are a separate design example. A second, explicitly fictional ledger demonstrates
monthly costs and a possible yearly insurance renewal in November 2026. Both
fixtures are generated by Python; they are not hardcoded frontend forecasts.
Today is highlighted using Europe/Riga. Financial date-only values are displayed
without time-zone shifts.

## Engine and API

`src/financial_calendar.py` exposes `build_financial_calendar(transactions, result)`.
It accepts one customer's existing financial result and eligible history, returns
the current month's remainder plus twelve future calendar months, and does not
change the forecast or deduct any calendar amount from it.

`POST /api/calendar` on the existing local Python server accepts the same request
as the financial engine's `POST /api/plan`, for example:

```json
{"customerId":"CUST00005","asOf":"2026-09-30","bufferCents":50000,"savingsTargetCents":10000}
```

It returns `events`, untouched `daily` balance estimates, forecast status and
coverage, buffer flags, and transaction evidence. Customer IDs and observation
cutoffs are checked by the engine; later and other-customer transactions are
excluded. The existing localhost prototype's authentication limitations remain.

The frontend uses `GET /api/calendar?source=engine` or `source=recurring` from
`ui-skeleton/api/calendar.js`. By default it serves saved engine examples from
`ui-skeleton/server/calendar`. To connect the running Python service, set
`FINANCIAL_ENGINE_URL=http://127.0.0.1:8765` in `ui-skeleton/.env.local`, restart
both servers with the latest code, then refresh the calendar. The Node adapter
requests the server-owned demonstration customer and cutoff. Arbitrary browser
customer IDs or upstream URLs are not accepted. A configured upstream failure
is shown as an error, not silently replaced by fixture data.

The domain builder can also render `plannedExpenses` from a supplied plan result:
matched/cancelled expenses are omitted; an already-included expense is merged
with a uniquely compatible forecast annotation using account, category, window
and exact amount. Unresolved links remain review items. The default frontend
endpoint does not load saved-plan state or accept expense edits. It is read-only.

## Recurrence rules and limits

Monthly rules reuse the profile engine's existing recurring-pattern detector.
Forecast annotations take precedence over the same pattern/month, preventing
the calendar from adding a second recurrence entry. Already-observed single
payments are suppressed for the remaining current month. Category groups such
as utilities keep a window; they are not labelled as identified providers.

Yearly candidates require at least two outflows for the same customer, account,
merchant, category and transaction type, successive gaps of 350–380 days, and
amount spread no greater than 10% of the median (or €1 for small costs). Stale
patterns and irregular gaps are withheld. A candidate has a ±7-day window and
always needs review. This is an explainable heuristic, not a trained annual
subscription model. Stable repeated purchases can still be unrelated purchases;
check the contract/merchant before relying on the recurrence. February and leap
years clamp dates safely. Missing merchant IDs cannot establish annual renewals.

Historical pattern reminders have no new forecast coverage claim and may already
be represented in historical scenarios. Do not sum them into the forecast.
There are no notifications, payment execution, external calendar sync, contract
cancellation, or production bank connection in this deliverable.

## Reproduce and verify

```sh
python3 scripts/build_calendar_examples.py
python3 -m unittest discover -s tests -p 'test_financial_calendar.py' -v
npm test --prefix ui-skeleton
```

Fixture regeneration requires the prepared local bank database. The second
example's history is built by `recurring_demo_rows()` in the generator. Tests
cover history isolation, amount/date boundaries, duplicate prevention, leap
years, sparse history, forecast integrity, API identity and upstream errors.
Browser checks cover both examples, filtering, evidence, daily balances,
navigation, mobile layout, failure retention, and the existing device preview.

The frontend integration is on the working branch. Pushing code does not update
the hosted Vercel app; deployment is a separate step.
